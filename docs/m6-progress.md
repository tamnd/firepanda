- [x] The argsort dtype, which #176 filed and which turned out to be a question about where a resource decision stops rather than a one line cast. The permutation a sort produces is uint32, one value per row, rewritten in full on every pass, and it is the largest temporary in the sort path, so on ten million rows the pandas width is eighty megabytes of ordinals instead of forty and the goal of using a tenth of the resources exists to refuse that. pandas returns int64 because numpy returns the platform index type and pandas uses a negative position as its sentinel for a row that is not there, a sentinel firepanda has no use for since a null is placed by `nulls_first` rather than removed and marked. So the kernel keeps uint32 and only `Series.argsort`, the one place a user reads the permutation rather than a sort consuming it, widens on the way out ([#178](https://github.com/tamnd/firepanda/pull/178)). `sort_values` was rerouted to `argsort_any` and pays nothing, and `DataFrame.argsort` is untouched because pandas has no such method to match
- [x] What the dtype was hiding. One of the two argsort cases still failed after the widening, and the cause was tie order: `keys_10` holds one duplicated value in ten thousand rows, firepanda's sort is stable and puts the earlier row first, pandas' default is a quicksort and puts the later one first, and `kind="stable"` reproduces firepanda's answer exactly. The case now names its kind, because pandas documents its default as not stable and an unstable sort's answer on a tie is one of several it is allowed to give, which is not a specification anything can be measured against. No divergence entry was written for it, deliberately: an entry has to be true every single time it runs, and this one would pin a claim about which permutation numpy's introsort happens to return, which a patch release is free to change. A second case was added on the key column instead, ten distinct keys over ten thousand rows, so that nearly every position in the answer is decided by the tie break rather than by a comparison, which is the property the first case leaves untested ([compat #34](https://github.com/tamnd/firepanda-compat/pull/34)). The stats section is 39 pass, 17 fail, 51 unimplemented over 107 runs
- [x] Half of #170, which is the largest single cause the suite has found so far and the first one that is a semantics decision rather than a defect. pandas has no separate presence bitmap for a float column, NaN is the only missing it has there, and firepanda has a bitmap for every dtype and so had a second spelling. A reduction with nothing to reduce came back null where pandas gives NaN, which nobody notices because `isna` says True to both and which is a different number the moment anybody does arithmetic on it. Thirteen reductions changed and the rule is keyed on the dtype rather than on the reduction: nine always answer in float64 and always take the NaN, and `min`, `max`, `first` and `last` keep the column's own dtype, so they take the NaN on a float column and keep the null on an int64 one, which has no NaN to write ([#179](https://github.com/tamnd/firepanda/pull/179)). Nineteen failures closed, basics from 120 pass and 57 fail to 131 and 46, stats from 39 and 17 to 47 and 9. The first version of the branch had the rule written as "answers in float64" rather than as "answers in a float dtype" and left the last four alone, and what caught it was the suite reporting `null, expected nan` on `basics/min` for an all null float column after everything else was fixed
- [x] The second time the instrument turned out to be wrong in a way only a subject could reveal, which is worth recording because both times the oracle was perfect while it happened. pyarrow converts a pandas object using pandas' own idea of missing, so a numpy float NaN became an Arrow null on the way in, on both sides of a comparison whose own message says a null is not a NaN. Four `groupby/flat-*` cases on `keys_awkward` had been passing because both sides were flattened to a null, not because the engines agreed, and they broke the moment firepanda started giving the pandas answer, which is how a fix that closed nineteen failures looked at first like a fix that opened four. A numpy float column is converted with pandas' rules switched off now and its NaNs arrive as NaNs ([compat #35](https://github.com/tamnd/firepanda-compat/pull/35)). An oracle run cannot find this class of bug at all, because both of its sides go through the same conversion and agree perfectly while being equally wrong
- [x] The other half of #170, which is the half about what goes in rather than the half about what comes back. pandas has no presence bitmap on a float column, so a NaN is the only missing it has there and `Series([1.0, nan]).count()` is 1, and firepanda followed Arrow and answered 2. `isna` said False on a NaN, `notna` said True, `dropna` kept the row, and `hasnans` said a column holding one had none. `is_null`, `is_not_null` and `all_valid_mask` read the values on a float dtype now, and the rule is written down once so that nothing has to repeat it, which is what makes `Series.null_count` count a NaN and `Array.null_count` not count it a stated line between the two halves of the library rather than an oversight: an `Array` is Arrow and says what is in the buffers, a `Series` is pandas and says what pandas would say ([#181](https://github.com/tamnd/firepanda/pull/181)). Seven failures closed, basics from 131 pass and 46 fail to 137 and 40, stats from 47 and 8 to 48 and 8. A bitmap word covers sixty four rows and only a word that a vector `isnan` says holds one is taken apart bit by bit, so a float column with no NaN in it pays one load, one compare and one reduce per vector and gets back the bitmap it started with. Four benchmark rows measure that, three of them new, because a read of the values buffer where there used to be none is a cost and not a detail
- [x] The third part of #170, which is where the cost is. The first two parts changed what a reduction hands back and what counts as missing when something asks; this one changes what the reductions read, and reading is the inner loop of every operation this library exists to make fast. `sum_over`, `mean_over` and `extreme_over` step over a NaN now, with a compare and a select per vector rather than a branch, so the loop shape is unchanged and there is no cost at all on any dtype that cannot hold a NaN ([#183](https://github.com/tamnd/firepanda/pull/183)). The mean needed the divisor as well as the total, so `_sum_range` hands back how many values it stepped over and the mean subtracts that from the count it was already given, which keeps it at one pass rather than two, and that subtraction is safe for a reason worth writing down: a null holds a zero and a zero is not a NaN, so no row can be taken away twice. The hard case was `_extreme_range`, where a full validity word used to be proof that something had been seen, and on a float column it is not any more, and the answer cannot be recovered from the folded lanes either because a block of nothing but NaN and a block holding one real infinity both fold to the identity. It carries a vertical mask of the lanes that held something real and reduces it once per block, and there is a test for each half of that pair. basics goes from 137 pass and 40 fail to 139 and 38, stats is unchanged at 48 and 8, and nothing opened. The delta is small because only two of the three float corpus frames have a NaN sitting in a row whose validity bit is set, which is most of what changed and is not something these cases can see. Three benchmark runs put the interquartile range on this section between 14 and 68 percent and every new float row lands inside the band the unchanged int64 rows occupy, so the honest statement is that the run to run spread is larger than anything the change could be costing rather than that it is free
- [x] The fourth part of #170, and the one that reached further than it was aimed. The grouped reductions still counted a NaN as a value and averaged it in, so `df.groupby(k).sum()` answered NaN for a whole group where pandas answers the total of the rows either side of it, which is harder to spot than the whole column version because one NaN in a million rows poisons one group and leaves the rest looking right. There was a real bug under it too: a group holding nothing but NaN reported `+inf` as its minimum, because `_extreme_core` carries its seen flags in the output bitmap and a NaN looked to it like a value it had seen, so the group came back marked valid with the identity still in it. Sixteen grouped reductions changed ([#185](https://github.com/tamnd/firepanda/pull/185)). Six failures close and four of them were not the target: `reduce_any` has a fast route for the reductions that finish in one pass and sends everything else to `aggregate_group_any` over a single group, and the order statistics are all in the everything else, so a whole column median or quantile is a grouped one with one group in it and learned the rule at the same time. basics goes from 139 pass and 38 fail to 141 and 36, stats from 48 and 8 to 52 and 4. No groupby case closes, and all 62 of them fail on the missing index name in #154 or the dictionary reader in #159, so the grouped NaN bug was found by reading the code and by the fuzzer rather than by the suite, which is a fair statement of where the suite is useful and where it is not. Where the test goes was measured rather than chosen, and the first answer was wrong: a corrected bitmap built in front of each reduction took a grouped float minimum from 321 to 491 microseconds, because the extra pass is two thirds as much memory traffic as the reduction it is helping, so the test sits in the loop instead where every core already about to load the value pays one compare for it and the same minimum costs about a tenth. `_count_core` is the one that keeps the bitmap, because a count reads no values and has no load to reuse, and `group/count_float` at 432 us against `group/size` at 227 is that cost rather than an artifact
- [x] The fifth part of #170, the fills, which is the worst place in the kernel for a NaN to be a value because a fill does not only report what is missing, it copies a value over it. So the mistake was made twice: the NaN row was left standing where pandas fills it, and then the NaN was picked up as the carry and ran forward over every null after it, so one NaN turned a gap that had a perfectly good value behind it into a run of NaN. `fill_forward` and `fill_backward` treat a NaN as missing on a float dtype now, and a row that could not be filled comes back as a null on an int64 column and a NaN on a float one, which is the rule [#179](https://github.com/tamnd/firepanda/pull/179) set for `min` and `first` and which a fill has more claim on than they do, since a fill's output is a statement about what is still missing afterwards ([#186](https://github.com/tamnd/firepanda/pull/186)). Where the test goes was measured again and the tidy answer was wrong again: correcting a whole validity word in front of the loop cost a clean float column 682 microseconds against 474 for the int64 column it should match, so it was thrown away for one that folds a vector `isnan` into the block copy that already has the values in registers and tests inline in the row loop, which is 489 against 489. Four cases close and they are two different bugs, `basics/bfill` on `float64_no_nulls` being the carry rule and the other three being the spelling, and basics goes from 141 pass and 36 fail to 145 and 32 with stats and groupby unchanged, which is what should happen since neither section fills. The fills had no fuzz coverage at all before this, which is a fair part of why the bug lasted, and the new check was confirmed to run by breaking the scalar twin on purpose and watching the fuzzer catch it ten steps in
- [x] Stage one of the index, which is the largest single cause the suite has ever reported and the one every other measurement in the groupby section was standing behind. firepanda had no index at all: a frame was a schema, some columns and a height, so `tail(5)` of a ten row frame came back labelled 0 through 4 where pandas labels it 5 through 9, `sort_values` threw the old labels away and `dropna` renumbered instead of leaving holes. `DataFrame` and `Series` now carry an `Index` and `take`, `filter` and `slice` carry it through, which covers `head`, `tail`, `sort_values` and `drop_nulls` since each of those is one of the three underneath ([#192](https://github.com/tamnd/firepanda/pull/192), driver side [compat #36](https://github.com/tamnd/firepanda-compat/pull/36), scoped in [#191](https://github.com/tamnd/firepanda/issues/191)). basics goes from 145 pass and 32 fail to 155 and 22, stats is unchanged at 52 and 4 because a scalar has no index, and groupby is unchanged at 54 and 62, and the shape of that 62 is the number worth reading: 57 of them read "0 index levels, expected 1" where before the reordered check they read "index names (), expected ('key',)" and named a level that was not missing a name but missing entirely, 2 say "expected 2" for the two key grouping which wants a MultiIndex, and the last 3 are the Arrow reader refusing a dictionary encoded column, which is #159 and is nothing to do with an index, so the whole of the section is one sentence now and the sentence is that a grouped result should be indexed by its key, which is stage two and nothing else. The design is two forms, an arithmetic range that is a start and a length with no memory at all, or an array of labels, and a frame only pays for the second when something takes it apart, which is what makes the field free on the path that does not use it. That was measured rather than assumed and the guess was wrong in both directions: against an untouched control that moved 4.6 per cent between the two binaries, `frame/take` moved 2.8 per cent and `frame/filter` moved 16.8 per cent, because a gather is a random read a row and a label needs no read at all while a compaction reads sequentially and was being prefetched anyway. Two earlier versions of the loops cost far more, 15.16 ms against 5.96 for the first and 46 and 129 per cent for the second, both because a frame level loop was written beside a kernel without meeting the kernel's standards, and both are recorded in the module docstring. The finding that matters most is not in the numbers: the change silently broke `group_by`, which is built out of a filter and a sort and so inherited labels it had no business keeping, and it came back labelled with the permutation of its group ordinals. All 47 firepanda test files passed with that bug present and the conformance suite caught it in one run, groupby falling from 54 pass to 14, which is the plainest argument this project has yet produced for running a conformance suite next to a unit suite rather than instead of asking for one. The rule that came out of it, and the one stage two has to hold to, is that an operation selecting rows carries labels and an operation producing rows makes them
- [x] Stage two of the index, which closed 57 conformance cases in one change and is the largest single move this project has recorded. A grouped result is now labelled by its key: `group_by`, `group_agg` and `group_count` take `as_index`, and with it on the key column becomes the frame's index, named after itself, with the aggregates as the only data columns ([#194](https://github.com/tamnd/firepanda/pull/194), driver side [compat #37](https://github.com/tamnd/firepanda-compat/pull/37)). The groupby section goes from 54 pass and 62 fail to 111 and 5, and the 5 that are left are worth naming because none of them is an index: 3 are the Arrow reader refusing a dictionary encoded column, which is #159, and 2 are the two key grouping, which pandas answers with a MultiIndex and firepanda has none, so `as_index` raises there rather than handing back one of the two levels and those cases stay in the flat spelling and keep failing on the level count, which is the truthful report. Across basics, stats and groupby the failure count is 31 now, down from 98 when the index gap was written up, and the index is no longer the largest cause of any of them. Two things came out of the work that the plan did not have. The first is that stage one shipped with a gap on the other side of its own rule: it said an operation that selects rows carries labels and an operation that produces rows makes them, and it had nothing to say about an operation that does not choose rows at all, so `select`, `drop` and `column` all threw the labels away and rebuilt a range. `df.groupby("k")["v"].mean()` is that case and it is the commonest single column shape in the suite, so stage two had to fix it before it could be measured, and eight of the thirty tests in the index file exist to hold it. The second is the `as_index` default, which is the one thing here that deliberately does not match pandas: pandas defaults it on, firepanda defaults it off, because turning it on by default would make a two key group by raise by default, and a shape that differs is a better answer than an operation that refuses. The other ten are all members of the pandas series and every one of them was missing here, which is not ten oversights but one missing thing: a column could not be handed to a frame. `series_to_frame` is that door and it is the third free function in `firepanda/py/frame.mojo` to exist for the same reason, which is that `frame.mojo` already imports `series.mojo` and Mojo will not take the cycle, while a method on the frame that takes a column and hands back a frame of that column reads backwards. Three functions now sit in that position and the shape is worth naming out loud: a door between two bound types belongs to neither of them, and the module is where it goes. The one thing that makes the ten members a line each rather than ten pieces of work is that the door copies the row labels across instead of leaving the range a fresh frame would carry. Every one of the ten either removes rows or reorders them, and the frame does the same thing to the labels that it does to the values, so not one of the ten has a line about the index anywhere. Nine of them are a call to a three line helper that puts the column in, runs the frame method, and takes the column back out under the name it went in with. `duplicated` is the tenth and is four lines rather than three, because what a frame answers there is a mask rather than a frame, so there is no column to take back and the mask is relabelled to the series' own name instead, which is what pandas does with the same pair of methods. `reset_index` is the one with two answer types, a column when the labels are dropped and a frame of two when they are kept, and that is pandas' rule rather than an invention: the labels have become values and values in a second column are what a frame is. The index then gets three more out of two doors end to end, `to_frame`, `duplicated` and `drop_duplicates`, and those three score twice on the board because `DatetimeIndex` subclasses `Index`. The rule that an index method hands back the class the index already was, which `dropna` wrote first in the entry above, is now in one helper rather than being written again each time. One divergence is recorded rather than hidden. pandas calls the column of an unnamed series `0`, the integer, and a column name in this library is a `String`, so it is the text of it, and a caller who writes `name=None` gets the same thing where pandas gives a column literally named `None`. Both of those close at once whenever a column name can hold something that is not a string, which is the same change `firepanda/frame/series.mojo` line 136 is waiting for and which the row read across the columns is also waiting for, so there is no reason to pay for it twice. The board went L3 45 to 54 and L2 102 to 116, with the parameter coverage 9.3 to 9.8 percent, on twenty seven cases spread over five case files because the section a name belongs to is pandas' answer and not this repository's. Two older cases moved in process in the same change and are worth the note. `stats/nlargest-series` and `stats/nsmallest-series` were written before the column had either method, were routed through the driver, and the driver never grew an entry for them, so they had been sitting unimplemented and stopping the climb for both names at L3 while the L2 cases below them passed. That is the second time the same shape has turned up, and it is worth watching for: a case written against a door that does not exist yet does not merely fail to score, it holds down everything above it. The same shape is why `Series.to_frame` passes at L2 and L3 and attains neither, since `nested/struct-to-frame` sits in its ladder and wants the struct dtype. What this deliberately does not reach is as interesting as what it does. `Series.groupby` is on the list of thirteen and is not here, because a frame's `groupby` names a column to group by and a series is grouped by something outside it, usually its own labels or an array the caller brings, which is real work rather than a line. `Series.filter` is not here either, because it filters the labels where a frame's filters the column names. And `Series.sort_values` is the next one to want, because it is `sort_index` on the frame this column and its own values make, it is what `Index.sort_values` also wants, and `DataFrame.sort_values` does not exist yet so neither does.
