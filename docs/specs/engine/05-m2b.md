# M2b, the chunked execution engine

This is the milestone. It is numbered M2b rather than getting a number of its own because it slots between M2 and M3 without renumbering the nine milestones after it, and because it is partly a pull forward of work that was sitting in M5 and M10.

## Why it exists

`01-what-we-take.md` has the argument. In one paragraph: firepanda runs one kernel over one whole column and writes a whole new column, which is pandas' execution model, and at ten million rows a column is eighty megabytes so every operator boundary is a full round trip through DRAM. Both rivals abandoned this. Polars measured three to seven times from the change alone. We are at five to nine times slower than DuckDB on joins with individually competitive kernels, and no amount of kernel work closes that.

## What it moves from where

M5 was parallel execution and M10 was streaming and out of core. M2b takes the morsel scheduler from M5 and the spilling from M10 and does them now, because they are the same design and doing them separately means building the scheduler twice.

M5 and M10 keep what is left, which is the wider operator coverage and the distributed pieces.

## Scope

### Foundations

- [ ] `ChunkedArray` becomes what a `Frame` column is, replacing the bare `AnyArray` list
- [ ] Every kernel gains a chunked entry point that walks chunks and calls the existing contiguous kernel per chunk, with the inner signatures unchanged
- [ ] Chunk size of 128 thousand rows when we create chunks, reader boundaries preserved when we do not
- [ ] A sortedness flag on a column, set by sort and by readers that know

### Scheduling

- [ ] `MorselQueue` with an atomic cursor, on top of the existing `parallel_for`
- [ ] `parallel_morsels(body, total, morsel_rows)` starting `worker_count()` tasks that each loop taking morsels
- [ ] Every kernel that currently slices into equal per worker pieces converted to it
- [ ] The worker count sweep rerun, to confirm the optimum moves from 24 back to 32 on a 32 thread machine

### Pipelines

- [ ] A `Node` interface of `update_state`, `process`, `finish`
- [ ] A `Pipeline` of source, operators, sink, executed by pushing chunks
- [ ] Pipeline cutting at breakers, found by one traversal
- [ ] A `Materialize` fallback node that collects chunks, calls the whole column kernel, and emits chunks, so that anything not yet ported still works

### Operators off the fallback

- [ ] Elementwise: filter, select, arithmetic, comparison, cast, with_column
- [ ] Group by, thread local partitioned tables merged partition wise
- [ ] Sorted group by, taken when the key is flagged sorted
- [ ] Inner and left join, build side consuming chunks, probe emitting as it goes
- [ ] Sort, consuming chunks and emitting chunks

### Selection vectors

- [ ] A chunk carries an optional selection vector
- [ ] Kernels read through it, in the shape of DuckDB's unified format
- [ ] `filter`, `take` and join output produce selections rather than copies
- [ ] A flatten threshold, chosen by measurement, for when a sparse selection is worse than a copy

### Memory and spilling

- [ ] A memory manager with a limit, an atomic total, `reserve`, `release` and `pressure`, counting only
- [ ] External sort
- [ ] External group by, partitions spilled and merged
- [ ] External join, build partitions spilled, probe rows routed and replayed
- [ ] A bail out for the skewed key case, where more radix bits do not separate a partition

### Ahead of all of it, as ordinary pull requests

- [ ] Salt bytes beside the pointer in the hash table
- [ ] Build side chosen by size rather than by argument order

### Holes closed along the way

- [ ] Top n per group, beside `group_ordinals`, which unblocks db-benchmark q8
- [ ] Merge join on two sorted inputs

## Exit criteria

- [ ] Every existing test passes with the engine on, and the `Materialize` fallback still present and still correct
- [ ] db-benchmark at 0.5GB and at 5GB on gamingpc, with the 5GB numbers reported as the headline, because the effect grows with size
- [ ] Group by queries at 5GB at least 1.5x their pre M2b selves
- [ ] Joins at 5GB at least 2x their pre M2b selves
- [ ] A group by over an input larger than the memory limit completes rather than failing
- [ ] A join over an input larger than the memory limit completes rather than failing
- [ ] q8 answered
- [ ] The worker count sweep shows no interior optimum

## What is deliberately not in it

A buffer manager. `03-memory-and-spilling.md` argues for operator controlled spilling instead, which is three operators rather than a subsystem every allocation goes through.

A lazy frame. The public API stays eager and the pipeline is built and run inside each call. Letting a user build a plan across calls is M3 and M4, and this design is what makes that a front end change rather than a second engine.

An optimizer. Polars measured about ten percent from cost based planning and it needs a plan to optimize.

Window functions. Real work, not this milestone.

Distributed and GPU. The honest single GPU number on a bandwidth bound workload is about three times with a mature engine underneath.

## The shape of the work

Not a rewrite with a flag day. The `Materialize` fallback means the system works from the first pull request, and every entry in the operator list above is one pull request that removes one fallback and has its own benchmark number.

That is how Polars did it. Their release notes from December 2025 to April 2026 are almost entirely one more operator lowered to streaming, one more sink made streaming, one more thing made out of core, twelve releases in a row, with the old engine as the fallback throughout. It is still the fallback at 1.39 and the streaming engine is still not the default. We should expect the same and plan for the fallback to be permanent rather than temporary.

## Depends on

M2. A streaming engine with no streaming source is a benchmark harness, and the Parquet reader is the first real source. This is also why Polars did sinks and sources before joins.
