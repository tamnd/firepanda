# 31. A window is a pair of rows

pandas has three window types, `Rolling`, `Expanding` and `ExponentialMovingWindow`, and puts twenty six reductions on each of the first two. The conformance board had every one of them at zero, which made `windows` the largest section in the suite sitting at nothing, and the obvious way to start on it is to pick a reduction and write it. That is the wrong first move, because it answers the smaller half of the question. What `rolling` and `expanding` are for is not the arithmetic. It is deciding which rows go together, and the arithmetic afterwards does not care which of the two asked.

So this document is about the pair of row numbers, and the reductions are the short part at the end.

## 1. The five parameters are one question

`s.rolling(window, min_periods, center, closed, step)` reads like five independent knobs and is not. Four of the five decide the same thing, which is the first row and the row after the last of the window that row `i` reduces, and the fifth decides which `i` are asked at all.

The base window that ends at row `i` runs from `i + 1 - window` up to `i + 1`, not including the last. Then:

`center` moves the far end forward by `(window - 1) // 2` before the near end is derived from it. That last clause is the part nobody guesses. A centred window of an even width is not symmetric, and it takes one row more from the left than from the right, so `rolling(4, center=True)` at row two covers rows nought through three. The floor division is where that comes from and pandas has the same one.

`closed` moves one or both ends by one row. `right` is the default and is the base window above. `left` moves both ends back, so the window at row `i` is the window at row `i - 1` under the default. `both` moves only the near end back, so it holds one row more than the width asks for. `neither` moves only the far end back, so it holds one row less, and a `neither` window whose `min_periods` is its full width therefore never answers anything. That last one looks like a bug the first time it is measured and is what pandas does.

`min_periods` does not move the window at all. It decides whether the window that was computed is allowed to answer, by comparing how many values it holds against the number given. Its default is where the two window types genuinely differ: a rolling window that is not told needs all of its rows, and an expanding window that is not told needs one. That is why `rolling(5).sum()` has four holes at the top and `expanding().sum()` has none.

`step` does not touch the window either. It decides which rows are asked, so the answer is `ceil(rows / step)` tall and carries the labels of the rows it kept. It is a property of the output rather than of the reduction, which is why it is the one parameter that changes the shape of what comes back.

Clipping happens after all of that and only against the column. The near end is derived from the unclipped far end, so a centred window at the bottom of the column loses rows rather than sliding back up the column to keep its width.

`Shape.edges` in `firepanda/kernel/window.mojo` is those five sentences as ten lines of arithmetic, and it is the only place in the library that knows any of it. Everything else takes a pair of row numbers.

## 2. An expanding window is a rolling one with no near end

Which means there is no second struct, no second resolver and no second loop. `expanding_shape(min_periods, rows)` builds a `Shape` whose width is the height of the column, whose near end therefore clips to row zero for every row, and whose other three parameters are the values that mean nothing. Everything after that is the rolling path.

The alternative is two implementations of the same reduction that agree today, and the way that fails is not that one of them is wrong on the day it is written. It is that the next parameter to arrive gets added to one of them.

The width is resolved against the column rather than at construction, and that is deliberate on the Python side too: `ExpandingMixin` holds `None` for the width and not the height. In pandas a window object holds a reference to a column that can grow before the reduction runs, so filling the width in at construction would be answering a question that has not been asked yet.

## 3. Why the reductions are carried and what that costs

Summing each window separately is the width times the height. Carrying a total, adding the row that arrives and subtracting the row that leaves is the height, and that is the whole reason anybody uses these rather than a loop. The edges are non decreasing in `i` for every combination of the five parameters above, including `step`, which is what makes the carrying legal at all.

Carrying costs something, and pandas pays it visibly. It pays it twice, for two separate reasons, and the two were worth separating because only one of them is about carrying at all.

The first is not about carrying and is the larger of the two. `pandas.core.window.rolling.BaseWindow._prep_values` contains three lines that replace every infinity in the column with a NaN before the kernel is handed anything, with the comment `Convert inf to nan for C funcs`. So an infinity in a pandas window is a missing value, and the window is reduced over the rows either side of it. Measured on pandas 3.0.5, `pd.Series([1, 2, inf, 3, 4, 5, 6]).rolling(3).sum()` is `[nan, nan, nan, nan, nan, 12, 15]`, where the last two are right and the three before them are not: the window at row three is `[2, inf, 3]` and its sum is an infinity, not a missing value. `pd.Series([1, inf, 2, 3]).rolling(2).max()` answers `1` and then `2` rather than the infinity twice. `count` is the one reduction of pandas' twenty six that does not see the replacement, because it reads the presence indicator and not the values, so pandas will tell you that a window holds two values and then answer the sum of one of them. This is specific to the window layer: `pd.Series([1, inf]).sum()` is an infinity and `.max()` is an infinity, and only `rolling` and `expanding` lose them.

The second is about carrying and is real. A running total is one number, so a finite column whose window total overflows to an infinity cannot come back from it, and neither can a sum of squared deviations. This does not copy either of them. The two infinities are counted rather than summed, the total carries only the finite rows, and the answer is assembled from the three at the end, so a window holding one sign sums to that infinity, a window holding both sums to a NaN, both survive the infinity leaving the window again, and the extremes answer the infinity, because an infinity in a column is an ordinary value. That leaves the finite rows overflowing on their own, which is rare and real, and the guard is to rebuild that one window from its rows, which costs the width of the window on the rows where it fires and nothing anywhere else.

I could not reproduce pandas' exact reset rule, because `pandas/_libs/window/aggregations` ships compiled and its `.pyx` is not in the wheel. Five candidate rules were written and measured against it and all five were disproved, including recomputing every window from scratch, which a single index on `[1, nan, 3, 4, nan, 6]` rules out. Reverse engineering it further would have produced a kernel whose specification is another kernel's rounding behaviour, so what is here is the mathematically correct thing and the differences are registered as divergences rather than chased.

## 4. Subtracting a row is not adding one backwards

A running sum that adds and subtracts loses precision in a way a running sum that only adds does not, because the error of the subtraction does not cancel the error of the addition that put the row in. A large value beside small ones is where it shows: after `1e16` and `1.0` have both been added, the `1.0` has been rounded away, and subtracting the `1e16` gives zero rather than one.

So the finite total is compensated, and the compensation is kept beside the total and added back at the end rather than being folded into the next row on the way in. That distinction is the difference between this working and not working. Folding it in is the textbook Kahan loop, and it rounds the incoming row against the compensation before adding it, so on this column the low bit is lost twice and is gone by the time the large row leaves. Keeping it beside the total, which is Neumaier's variant, means the bits are still there to add back. `test_the_low_bits_survive_a_row_leaving_the_window` is that column, and it fails under the textbook loop.

## 5. The extremes are not summable and are not recomputed either

Knowing the maximum of a window and the value that just left does not give the maximum of what remains, so there is nothing to subtract. Recomputing is the width times the height and gives back everything section 3 bought.

The standing answer is a deque of row numbers whose values decrease from front to back. A row arriving evicts every row behind it that it beats, because a row that is both older and smaller can never be the answer again, and the front of the deque is dropped once it falls out of the near end. Every row is pushed once and popped once, so the pass is the height of the column no matter how wide the window is. The deque is an integer array the height of the column with a head and a tail index, rather than a list that grows, because its maximum size is known before the first row is read.

## 6. A carried variance needs to know when to stop being carried

`var`, `std` and `sem` are one reduction with three endings, because pandas writes `std` as the root of the variance and `sem` as the deviation over the root of the count, and its own `sem` is four lines of Python doing exactly that. So there is one state and one loop, and the three form codes pick the ending.

The state cannot be a total, because the mean moves when a row arrives or leaves and every squared deviation already folded in was measured against the old mean. That rules out the shape section 3 uses. Three things were considered and two were rejected.

The sum of squares, recovering the variance as the mean of the squares minus the square of the mean, is one number and one subtraction and is not good enough. `group.mojo` already argues that for a whole column, and a window makes it worse rather than better: the window is narrower than the column, so the variance being recovered is smaller, while the sum of squares it is recovered from is the same size. On a pair of rows holding `1e15` and the next double above it, which differ by one, it answers nought where the answer is a half.

The two pass form, which is what `group.mojo` does, subtracts each group's own mean and then corrects for the centre it used. That is the accurate answer and it is not available here at any price worth paying, because the second pass would run once per window rather than once per column, and a window five hundred rows wide would cost five hundred times the column. One pass is the reason anybody calls these, so one pass is the constraint.

What is here is Welford's method with the removal run as the update backwards, and the mean carried with a compensation for the reason section 4 gives. Running an update backwards does not undo it, and where it goes wrong is worth naming because it is not the usual slow drift. A window holding one large value and several small ones has almost all of its squared deviation belonging to the large value. When that value leaves, what is subtracted is nearly the whole of what is there, and the small number left over is the difference of two large ones, so every digit of it can be wrong. On `[1e8, 1, 2, 3]` with a three wide window, the window over one, two and three has a variance of one and the carried state gives three quarters.

So the state carries a fourth number, which is a bound on how much error the updates could have introduced. Each update adds the rounding error it could have made, which is the machine epsilon times the size of the term folded in plus the size of the answer it was folded into. When that bound grows past a hundred millionth of the answer, the state is no longer worth carrying and the window is rebuilt from its own rows. This is the same shape as the overflow guard in section 3 with a real bound in place of a test for infinity, because a variance loses its digits long before it reaches one. On ordinary columns the bound grows by a few epsilons a row and a rebuild fires about once in twenty thousand rows. On adversarial ones it fired on 4.3 percent of steps across a sweep of 54738 runs, with a worst single column of 0.8, and it fires on the rows where it is needed.

Two answers are read off the count rather than out of the accumulation, because a rounding either side of nought is very visible next to a nought. A window holding one value has no spread, and a window whose values are all the same has a variance of exactly nought. The state counts how many of the values handed to it most recently were the same value, and a window whose run reaches its own height answers nought without reading the carried number. The run is not shortened when a row is dropped and does not need to be, because the values in a window are always the ones handed over most recently, so a run that reaches the height of the window covers the whole of it however long ago it started. pandas does both of these and for the same reason.

The infinities are counted rather than folded in, exactly as section 3 counts them for the total, and a window holding any of them answers NaN. That is not a convention: the mean of a set holding an infinity is an infinity, every deviation from it is an infinity minus an infinity, and there is no number there. It matters more here than it does for a total, because one infinity folded into a sum of squared deviations turns it to NaN and no later subtraction brings it back.

This was validated rather than argued. The algorithm was prototyped in Python and run over 54738 window configurations and 457533 steps, compared both against pandas and against an exact answer computed in fractions. Every disagreement with pandas, 3999 of them, is one where this answer is within the suite's statistical tolerance of the exact answer and pandas' is not. There are no cases the other way round and none where both are wrong. A hundred and seventy four steps are outside that tolerance of the exact answer, all of them on columns like `[1e10, 1e10 + 1, ...]` where one pass in double precision is inherently about 5e-7 out and pandas shows the same error, so they are inherent to one pass rather than a defect of this one.

Where the two differ on purpose, the differences are registered. pandas answers a finite number for a window holding an infinity, as section 3 explains, and is not even consistent with itself across the degrees of freedom while doing it: the same windows are NaN at `ddof=1`, because one surviving value leaves no divisor, and nought at `ddof=0`, because one surviving value leaves a divisor of one. And a pandas sum of squared deviations that overflows stays infinite for every later window, so `[1e200, 1e200, 1, 2, 3]` with a two wide window answers an infinity for the last two rows where the answer is a half.

## 7. Why `ddof` is the last argument this door can take

`ddof` belongs to the reduction and not to the window, and it crosses the boundary beside the five that do describe the window, because there is one door and not twenty six. With it there, `PySeries.window_agg` takes seven arguments after the object, which document 13 section 4 measured as exactly the ceiling: `PyObjectFunction` carries overloads up to eight arguments, and for a bound method `py_self` is one of the eight.

So this is the last positional window parameter. Whatever the next one is, it comes through `var **kwargs: PythonObject`, which does not count against the ceiling and which document 13 measured as working alongside the seven. That is worth writing down here rather than discovering it while adding `skew`.

The Python side spends its one exception here too. pandas takes a float for `ddof` and truncates it, so `var(ddof=1.5)` quietly answers the `ddof=1` column, and a caller who wrote that meant something and did not get it. A whole number is asked for and anything else is an `InvalidArgumentError`. A negative one is accepted, as it is in pandas, because a divisor larger than the count is a strange question rather than a malformed one.

## 8. What a missing row is, and the one place `count` reads differently

Whatever `present_bitmap_any` says, which on a float column means a NaN counts as holding nothing. That is already the library rule and it is also pandas', so none of the reductions here has to think about NaN at all: a missing row is not added to the total, not pushed into the deque and not counted toward `min_periods`.

`count` is the exception, and the difference is not a decision made here. pandas computes it as a rolling sum over the presence indicator, which is a column with nothing missing in it, so what `min_periods` is tested against is how many rows the window covers rather than how many hold a value. Measured on `[1, nan, 3, nan, 5, 6]`, `rolling(3).count()` is `[nan, nan, 2, 1, 2, 2]`: row three holds one value out of three rows and answers one, where `rolling(3).sum()` on the same column is missing everywhere. The kernel gates `count` on the slot count for exactly that reason, and it is the one line in the file that would look like a mistake without this paragraph.

## 9. The answer is always float64

Every window reduction answers float64 in pandas, including `count` and including the extremes over an int64 column, because there is nowhere else to put the holes at the top. So the column is cast once on the way in and there is one loop rather than one per dtype.

That is worth saying out loud because it is the opposite of what `cumulative.mojo` does, which monomorphizes over every dtype and is right to, since a cumulative sum over int64 answers int64. It also sidesteps the compile time hazard document 03 describes, where a helper reached from a dtype dispatch that calls back into the dispatch makes the compiler take unbounded time. There is no dispatch here to call back into.

A missing row in the answer is a NaN with no validity bit behind it, which is what every float column in this package holds and what `nan_over_nulls` exists to say.

## 10. The Python surface, and the four arguments that are declared and refused

`rolling(...)` takes nine arguments and this implements six of them. `win_type` asks for a weighted window, which is a different kernel rather than a parameter of this one, and pandas needs scipy for it. `on` says to order the window by another column, and on a frame it also carries that column through into the answer unreduced. `method` chooses between reducing the columns separately and reducing them together, and this library reduces them separately. All three are declared and refused by name, on the rule document 18 section 4 sets: the signature parity check compares the whole parameter list against a running pandas, and a caller who passes one should get a sentence about it rather than a TypeError about an unexpected keyword.

`on` is worth a sentence more than the other two, because on a frame it does something this library could write and still should not. Copying the named column into the answer is easy and ordering the window by it is the point, and ordering by a column means a window given as a duration, which needs a calendar first. A `rolling` that accepted `on` and silently went on counting rows would be the cosmetic half of the argument with the load bearing half missing, which is worse than not having it.

`engine` is the fourth, on the reduction rather than on the constructor. `numba` is refused and `cython` is accepted, because `cython` names the path this library is already on.

`numeric_only` is one name asking two questions and it gets a different answer on each. On a column it says to refuse a column that is not a number, and every reduction here already refuses one, so the two values agree everywhere this library has an answer and both are accepted. On a frame it says to drop the columns that cannot be reduced rather than refuse them, which is a decision about which columns come back rather than about what a reduction means, so it is held at False and True is refused. That is the same rule the group by path already follows and it is the same sentence there. One method with two rules is worth flagging and it is not an inconsistency: the argument genuinely means two things and pandas spells both of them with one word.

The five arguments that do describe a window are checked in the constructor and not at the reduction, because that is where pandas checks them. `s.rolling(-1)` raises out of the `rolling` call and not out of the `.sum()` after it, and a program that catches the wrong line is a program whose error handling does not run. Each of the five messages is pandas' own sentence, and each is an `InvalidArgumentError`, which is a `ValueError`.

There is one check that is not pandas'. pandas accepts `step=0` when the window is built and divides by it when the reduction runs, so what a caller sees is a `ZeroDivisionError` out of `.sum()` with nothing in it naming the argument that caused it. A step of nought asks for the same row forever, so it is refused where the other four are.

The kernel checks the same five again on the way in. That is not duplication worth removing: one of the two checks exists to be reached from Python and the other exists because the Mojo API is a public entry point of its own.

## 11. A window object reports what it was given, not what it resolved to

pandas puts eleven read only properties on a window object and code in the wild reads them, mostly to find out what a window it was handed is going to do before asking it to do it. Six of the eleven are the arguments handed straight back. The other five are `method`, `win_type`, `on`, `ndim` and `exclusions`, and four of those are constant here because they describe a choice this library made once rather than a choice per window.

The six that are arguments are kept exactly as they arrived, and that is a real decision rather than laziness. `df.rolling(2).closed` is None in pandas and not `right`, and `df.rolling(2).min_periods` is None and not two, even though both windows behave as though the default had been written. Resolving them when the object is built would report a decision as though it were an argument, and a caller reading `min_periods` to find out whether one was set would get the wrong answer. So the defaults are applied one line later, on the way to the kernel, where nothing can read them back.

`ndim` is the one property whose answer depends on which of the two owners built the window, and it is the only place outside the reduction where that has to be known.

## 12. The frame form is the columns windowed one at a time

`df.rolling(3).sum()` is `s.rolling(3).sum()` run once per column and the answers put back beside each other. That is not a shortcut, it is what a window is: a pair of row numbers, and every column of a frame has the same rows. There is nothing a frame window can compute that a column window cannot, which is why `method="table"`, the argument that would ask for the columns to be reduced together, is the one that is refused.

So there is one `Rolling` class and one `Expanding` class here where pandas has two of each, and they hold a column or a frame without much caring which. Two places care. The reduction has a different class to hand back. And `numeric_only` asks a question a frame can answer and a column cannot, which section 10 argues.

The one thing that is not per column is the refusal. Every column is checked before any of them is read, so a frame with a text column at the end of it raises instead of computing half an answer and then raising. The wasted work is not the point, since these reductions are cheap and the half answer is thrown away either way. The point is that a caller who gets an error should not have to wonder what was already spent, and the cost of getting this right is a loop that does nothing but check.

The message names the column. pandas says `Cannot aggregate non-numeric type: str`, which over a frame of forty columns sends the reader back to look for the column themselves, and the column name is the one piece of information the error has that the caller does not.

Two smaller things follow from putting columns back together rather than reducing a frame as a frame. A frame of no columns is handed back rather than rebuilt, because rebuilding nothing makes a frame of no rows and that is a different frame. And the row labels are taken off the first answered column rather than off the frame that was read, because a step makes the answer shorter and gives it the labels of the rows it sampled.

## 13. One door, and the width is what picks the window type

There is one bound method under both classes and one function behind it, and an absent width is how an expanding window is spelled. That is the same shape `text.mojo` uses for a slice bound, and it is chosen for the same reason: the alternative is a flag beside the width saying which of them to believe, which is a parameter that exists to say that another parameter does not, and those are the ones that get out of step.

`min_periods` also crosses as an absence, because its default is not one number. Filling it in on the Python side would mean the layer that does not own the rule owns the rule.

There are two doors rather than one, `PySeries.window_agg` and `PyDataFrame.window_agg`, taking the same seven arguments and differing in what they read and what they answer. That is two because the boundary is typed and not because the question is, and the frame one is nine lines that call the column one in a loop.

The two Python classes are generated from one table entry each and share a `WindowMixin` that holds the data and the five numbers. They differ in their constructors and in nothing else.

## 14. The eleven that are here and the fifteen that are not

`sum`, `mean`, `count`, `min`, `max`, `var`, `std`, `sem`, `skew`, `kurt` and `median`. They are eleven rather than some other number because they are the ones a window can be carried through: the answer to a window can be derived from the answer to the window before it and the rows that changed. The first five carry a number, the next five carry a state, which sections 6 and 15 are about, and the eleventh carries a count of the window's values by rank, which section 16 is about.

`quantile` and `rank` read out of the same structure the median reads out of and are waiting on room at the Python door rather than on anything in the kernel, which section 16 also covers. `apply` needs a Python callable per window. `corr` and `cov` take a second column. `aggregate` is surface rather than kernel, and so is a `numeric_only` that drops columns rather than refusing them. The exponentially weighted window has no edges at all and shares nothing with any of this. A window given as a duration rather than a count needs a datetime index to measure against, and a window under a group by needs the row numbers restarted per group.

None of them resolves rather than resolving and refusing, for the reason document 07 gives: an absent name reads as unimplemented on the board and a refusing one reads as a failure, and the second is a worse thing to say about work that has not been done.

## 15. The third and fourth moments are section 6 twice more, with a tighter bound

`skew` and `kurt` are one reduction with two endings, the same arrangement `var`, `std` and `sem` have, and they hold the variance state rather than repeating it. The recurrence that adds a value to a carried third and fourth central moment is standard and the removal is that recurrence run backwards, so sections 4 and 6 are the whole design and this section is only what had to change.

Two things had to change. The first is that there are two answers to bound rather than one, so the state carries a bound for each moment and rebuilds when either has outgrown its own answer. The second is that the bound of section 6 was not tight enough at this power. That bound counts the rounding of its own additions, which is the right accounting for a sum of squared deviations and an incomplete one for a cube, because the term being folded in is itself built out of `value - mean` and that subtraction is where the digits go. A window holding eight hundred and seven hundred and ninety loses most of a deviation to cancellation before it is cubed, and cubing multiplies whatever relative error the deviation had by three. So the state now measures that cancellation directly, as the machine epsilon times the sizes of the two operands over the size of their difference, and propagates it by three for the cube and by four for the fourth power.

Measured against exact rational truth on a column of four thousand values with three spikes in it, the bound of section 6 at a hundred millionth let a carried kurtosis drift into the ninth digit while pandas held the eleventh. With the cancellation counted and the threshold tightened to a millionth of a millionth, the skewness holds the thirteenth digit and the kurtosis the twelfth, both of them ahead of pandas, and the rebuild fires on eight rows in a hundred at a width of three, on four in a hundred at a width of four, and on one in a thousand from a width of thirty two up. The threshold is four figures tighter than the one the variance uses and it buys three more digits than a threshold one figure tighter again would, at half the rebuilds, which is why it sits where it does.

The cost stays bounded whatever the column does. A rebuild reads the window once and the row is then answered whether the rebuilt state settled or not, so the worst a pass can cost is what recomputing every window from scratch would have cost, which is the guarantee section 3 needs and the one a rebuild that retried could not give.

Head to head against pandas on the same two columns: on a four wide skewness this answers thirty four times closer to the truth, on a four wide kurtosis the two are level, on a three wide skewness pandas is closer, and on a column of values near a hundred million stepping by a thousandth this is between seven and forty seven times closer on all three. pandas reconstructs its moments from raw sums of powers, so the column that hurts it is the one where the values are large and the spread is not, and that is the column a carried central moment is for.

Two answers are read off the count here as well, and they are not the same kind of thing as each other. A constant window has no shape, and a skewness of nought for it is right because a constant is symmetric. A kurtosis of minus three for it is not right by any reading, because the standardized fourth moment of a real distribution is never below one and the excess is never below minus two. It is what pandas answers, and it is copied for the reason document 07 gives about surfaces: a caller comparing the two libraries on a column of one repeated value would read a NaN here as a defect here. pandas does not even agree with itself about it, since the same rows through `Series.kurt` with no window at all answer nought.

One difference is deliberate and is registered. pandas refuses to give either shape to a window whose population variance is at or below ten to the minus fourteen, and that threshold is absolute rather than relative, so whether pandas will tell you the shape of your readings depends on the units you recorded them in. Four readings alternating by a hundredth of a micron have a kurtosis of exactly minus six and pandas answers NaN, while the same four readings scaled up by eleven answer minus six. A one pass sum of powers cannot compute a shape down there, so the threshold is doing real work for pandas, and a carried central moment with a rebuild does not need it. Below the point where the squared deviations themselves underflow to nought there is no ratio to take and both libraries answer NaN, which is the one place the two agree about refusing.

## 16. The median is a count of ranks, and the other two order statistics read out of the same count

`median`, `quantile` and `rank` are the three window reductions that are not folds. There is no number and no state you can carry from one window to the next and correct for the rows that changed, because the answer is a position in the sorted window and one row arriving can move that position past any number of values. So sections 3 through 6 do not apply to them, and what does apply is one structure that all three read out of.

pandas keeps a skip list per column and inserts into it and deletes from it, which costs the logarithm of the width per row and is the right structure for a stream of values arriving one at a time. A window here is not a stream. The whole column is in memory before the first window is formed, so its values can be ranked once, and a window can then be a count of how many values it holds at each rank rather than a collection of the values themselves. That count is held as a Fenwick tree, where adding a row is one update, dropping one is another, selecting the k-th smallest value is one descent, and counting how many values a row beats is one prefix sum. Every one of those costs the logarithm of the number of distinct values in the column, so the pass is n log n whatever the width, against n log w for a skip list and n times w log w for sorting each window separately.

That structure is also the one place in this document where a reduction has nothing to lose. A count of values is exact, it stays exact however long the pass runs, and a large value leaving the window takes no digits with it. So there is no error bound here, no rebuild, and none of section 6's argument about when a carried thing stops being worth carrying. The loop is shorter than the loop for a variance and it is shorter for a reason rather than by accident.

The rows that change are written as the difference between the last window and this one rather than as two runs either side of it. That distinction only matters for a `step` wider than the window, where two consecutive windows share no rows at all: written as a difference the loop drops everything the last window held and adds everything this one holds, which is right, and it never has to walk the tree to zero it. Clearing a Fenwick tree costs the number of distinct values in the whole column, and paying that per answered row would make a stepped median dearer than sorting each window from scratch, which is the thing the structure exists to avoid.

The median of an even window is the mean of its two middle values and there are two ways to write that. The sum of the two over two is what pandas does, and it overflows when both values are near the top of the float range, so a window holding the largest finite double twice has a median of infinity in pandas. Half of each value does not overflow, and it lands one bit away from the sum over two on ordinary data because the two roundings fall in different places. So it is written as the sum over two, which agrees with pandas to the bit everywhere the sum is a number, and the halves are used only in the window where that sum came out infinite and both values were finite. That is one window on one shape of column, it is the same disagreement the running total of section 3 has and it is resolved the same way, which is to give the answer that is right.

The infinities disagree here for the reason they disagree everywhere else in this document. pandas replaces every infinity in the column with a missing value before it forms a window, so to pandas a window holding an infinity is a shorter window and its median is the median of the rows either side. Here an infinity is a value, it sorts above every finite one, and the window holding it has one more value than pandas thinks it does. The window after the infinity has left agrees again, because there is nothing accumulated for it to have spoiled.

`quantile` and `rank` are already written against this structure and are not on the surface yet, and the thing stopping them is the door rather than the arithmetic. `quantile` adds a required fraction and an interpolation word, and `rank` adds a method word, a direction and a percentage flag, and section 7 measured the seventh slot after the object as the last one a bound method has. So the reduction's own parameters have to stop being separate arguments and become one value that the Mojo side reads apart, which is a change to the door that every one of the eleven passes through and is worth doing on its own rather than alongside a new reduction. Two things about them are already settled and worth writing down. `rank` ranks the value at the window's last row rather than the value at the answered row, which is visible under `closed='left'`, where the last row of the window is the row before the answered one, and under `center=True`, where it is a row after it, and it makes `rank` the one reduction that reads a row rather than a window. And pandas' window `rank` takes only `average`, `min` and `max` where `Series.rank` also takes `dense` and `first`, which is pandas' own restriction and is copied, because the two words it drops need an ordering over the whole column and a window does not have one.
